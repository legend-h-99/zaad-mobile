serves unknown paths from `404.html`. After building, the deploy step must publish
`dist/` to the Pages repo **and** create `404.html` (copy `index.html` or
`+not-found.html` → `404.html`) so unknown URLs still fall back to the app. Known
routes (`/login`, `/register`, `/reset-password`, …) now have their own HTML and
return HTTP 200 without any fallback.

## Dependency & sequencing notes

- **001 hard-depends on 010** (discovered while executing 001 on 2026-07-30):
  `app/+html.tsx` is only rendered when `web.output` is `static`/`server`, which
  plan 010 sets. Under Expo's default SPA export the CLI writes `index.html` from
  a hardcoded `lang="en"` template and ignores `+html.tsx`
  (`@expo/cli/.../export/exportApp.js:142-145`). **Do 010 before 001.** If 010
  falls back to Vercel SPA rewrites (keeps `output: single`), 001 needs a
  different approach — see the fallback caveat in plan 001.
- **Plans 002–007 all edit `app/(auth)/login.tsx`.** Run them **sequentially**,
  not in parallel — each plan's "Current state" excerpts assume the file is
  otherwise unchanged. Re-run the drift check at the top of each plan before
  starting it.
- **010 → 001 are blocked on a real static-render incompatibility (needs 012 or Vercel).**
  Two execution attempts proved it: with `web.output: static`, `expo export`
  server-renders every route in Node and crashes because `src/lib/supabase/client.ts`
  instantiates the Supabase client at module scope, whose web storage adapter calls
  `globalThis.localStorage.getItem` during the render pass (no functional
  `localStorage` in Node). Two ways forward:
  - **Plan 012 (recommended for GitHub Pages):** make the Supabase client
    static-render-safe — lazy-init it (create on first use, not at module load)
    and/or guard the storage adapter with `typeof globalThis.localStorage?.getItem
    === 'function'`. Then retry 010 → 001. Risk: static rendering may surface
    further module-scope browser access elsewhere (whack-a-mole).
  - **Vercel fallback:** keep `output: single` and deploy the web build to Vercel
    with a catch-all rewrite to `/index.html` (returns HTTP 200 for every route).
    The sibling repo `zaad-mobile-live` already has a `vercel.json`. This fixes the
    404-status goal without static rendering, but leaves `+html.tsx` (001) inert —
    RTL `<html>` would then need a tiny post-build script patching `dist/index.html`.
- **008 is softly improved by 010**: the password-reset email link lands on a web
  route; after 010 that route returns HTTP 200 instead of 404. 008 still works
  without 010 (the page renders via the 404 fallback), so 010 is not a hard
  blocker — but do 010 first if doing both.
- Revised quick-win sequence: **010 → 001**, then the login.tsx cluster 002, 003,
  004, 005, 006, 007 (all S, sequential), then 009 and 008.

## Findings considered and rejected

- **Exposed `EXPO_PUBLIC_SUPABASE_ANON_KEY` in the bundle** — not a leak. The
  `EXPO_PUBLIC_` prefix is designed to ship in the client bundle; the Supabase
  anon key is a public key protected by Row-Level Security. `.env.local` is
  correctly gitignored (`.env*.local`). No action.
- **Apple `authorizationCode` passed as `access_token`** in `AppleSignInButton`
  — investigated; harmless with Supabase's `signInWithIdToken`. Not worth a plan.
